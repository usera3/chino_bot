# zhinai-bot-v3 架构设计 - 管家模式

## 🎯 核心理念

**v3 = 智能管家中枢 + 插件生态**

- **管家（Butler）**: 理解需求、规划任务、调度插件、整合结果
- **插件（Plugins）**: 提供具体功能实现（情感、角色扮演、邮件、天气等）
- **大模型**: 管家的"大脑"，负责推理和决策

---

## 🏗️ 架构对比

### ❌ 传统架构（new-bot）
```
用户消息 → Agent → 内置功能（情感、工具等）→ 回复
```
**问题**: 功能耦合，难以扩展

### ✅ 管家架构（v3）
```
用户消息 → Butler（管家）→ 插件调度 → 插件执行 → 结果整合 → 回复
              ↓
         LLM 推理决策
```
**优势**: 功能解耦，插件化，易扩展

---

## 🤖 核心组件

### 1. Butler（管家中枢）

**职责**:
- 理解用户意图
- 分析任务需求
- 规划执行步骤
- 调度插件执行
- 整合执行结果
- 生成最终回复

**不负责**:
- ❌ 具体功能实现（交给插件）
- ❌ 数据存储（交给插件）
- ❌ 业务逻辑（交给插件）

**实现**:
```python
class Butler:
    """智能管家 - 中央调度器"""
    
    def __init__(self, llm, plugin_manager):
        self.llm = llm  # 大模型（推理引擎）
        self.plugin_manager = plugin_manager  # 插件管理器
        self.react_agent = ReActAgent(llm)  # ReAct 推理
    
    async def process(self, user_input: str) -> str:
        # 1. 理解意图
        intent = await self._analyze_intent(user_input)
        
        # 2. 规划任务
        plan = await self._create_plan(intent)
        
        # 3. 调度插件
        results = await self._execute_plan(plan)
        
        # 4. 整合结果
        response = await self._synthesize_response(results)
        
        return response
```

### 2. Plugin Manager（插件管理器）

**职责**:
- 插件注册与发现
- 插件生命周期管理
- 插件调用路由
- 插件依赖管理

**实现**:
```python
class PluginManager:
    """插件管理器"""
    
    def __init__(self):
        self.plugins = {}  # 已注册插件
        self.tools = {}    # 插件提供的工具
    
    def register_plugin(self, plugin: Plugin):
        """注册插件"""
        self.plugins[plugin.name] = plugin
        # 将插件的工具注册到工具表
        for tool in plugin.get_tools():
            self.tools[tool.name] = tool
    
    def discover_plugins(self):
        """自动发现插件（扫描 plugins/ 目录）"""
        pass
    
    async def call_tool(self, tool_name: str, **kwargs):
        """调用工具"""
        tool = self.tools.get(tool_name)
        return await tool.run(**kwargs)
```

### 3. Plugin（插件基类）

**标准接口**:
```python
from abc import ABC, abstractmethod
from langchain.tools import BaseTool

class Plugin(ABC):
    """插件基类"""
    
    @property
    @abstractmethod
    def name(self) -> str:
        """插件名称"""
        pass
    
    @property
    @abstractmethod
    def description(self) -> str:
        """插件描述"""
        pass
    
    @abstractmethod
    def get_tools(self) -> list[BaseTool]:
        """返回插件提供的工具列表"""
        pass
    
    async def on_load(self):
        """插件加载时调用"""
        pass
    
    async def on_unload(self):
        """插件卸载时调用"""
        pass
```

## 🔄 工作流程

### 示例 1: 简单对话

```
用户: "你好"

Butler:
1. 分析意图 → 简单问候
2. 规划任务 → 需要角色扮演 + 情感系统
3. 调度插件:
   - RolePlayPlugin.GetRolePromptTool() → 获取角色人设
   - EmotionPlugin.GetEmotionTool(user_id) → 获取情感值
4. 整合结果 → 生成符合角色和情感的回复
5. 回复: "你好呀~主人！今天心情怎么样？"
```

### 示例 2: 复杂任务

```
用户: "帮我查一下北京明天的天气，如果下雨就发邮件提醒我带伞"

Butler:
1. 分析意图 → 天气查询 + 条件判断 + 邮件发送
2. 规划任务:
   Step 1: 查询天气
   Step 2: 判断是否下雨
   Step 3: 如果下雨，发送邮件
3. 调度插件:
   - WeatherPlugin.GetForecastTool(city="北京", date="明天")
     → 结果: {"weather": "雨", "temp": "15-20°C"}
   - 判断: weather == "雨" → True
   - EmailPlugin.SendEmailTool(
       to="user@example.com",
       subject="明天记得带伞",
       body="北京明天有雨，记得带伞哦~"
     )
4. 整合结果
5. 回复: "北京明天有雨，温度15-20°C，我已经发邮件提醒你带伞了~"
```

## 🎨 架构优势

### 1. 高度解耦
- 管家只负责调度，不关心具体实现
- 插件独立开发、独立测试、独立部署
- 插件可以随时添加/移除

### 2. 易于扩展
- 新功能 = 新插件
- 集成 NoneBot 插件 = 写个适配器
- 插件数量无上限

### 3. 标准化
- 所有插件遵循统一接口
- 所有工具基于 LangChain Tool
- 管家调用方式统一

### 4. 可维护性
- 插件故障不影响管家
- 插件可以独立更新
- 清晰的职责边界

## 🚀 实现策略

### 阶段 1: 管家框架（核心）
**目标**: 实现管家中枢和插件管理器

**任务**:
1. 实现 `Butler` 类（管家中枢）
2. 实现 `PluginManager` 类（插件管理器）
3. 实现 `Plugin` 基类（插件接口）
4. 实现插件自动发现和注册
5. 集成 LangChain ReAct Agent

**验收**: 管家可以加载插件并调用工具

---

### 阶段 2: 核心插件（伪代码）
**目标**: 实现核心插件的接口和伪代码

**任务**:
1. 情感系统插件（伪代码）
2. 角色扮演插件（伪代码）
3. 记忆系统插件（伪代码）

**验收**: 插件接口定义清晰，可以被管家调用

---

### 阶段 3: NoneBot 插件适配器
**目标**: 自动集成 NoneBot 插件商店的插件

**任务**:
1. 实现 `NoneBotPluginAdapter`
2. 自动扫描已安装的 NoneBot 插件
3. 将 NoneBot 插件转换为 v3 Plugin
4. 测试常见插件（邮件、天气、定时任务）

**验收**: NoneBot 插件可以自动转换并被管家调用

---

### 阶段 4: 实际功能实现
**目标**: 用真实插件替换伪代码

**策略**:
- 优先使用 NoneBot 插件商店的插件
- 如果没有合适的，再自己实现
- 保持插件接口不变
